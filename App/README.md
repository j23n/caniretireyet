# The app

The SwiftUI app for iPhone, iPad and Mac (iOS 26 / macOS 26), on top of the Swift package in the repository root. Read [docs/UI.md](../docs/UI.md) for what it looks like, and this file for how it's built and where your code goes.

Build it on a Mac: `brew install xcodegen && xcodegen` in the repository's root, then open `CanIRetireYet.xcodeproj`. The project is generated from [project.yml](../project.yml) at the root and never committed.

## At a glance

```
CanIRetireYetApp (@main)          one AppModel, injected into every scene
 └─ RootView                      launch · onboarding · main navigation
     ├─ TabRoot (compact)         Overview · Accounts · Plan tabs, check-in in the tab bar accessory while due
     └─ SidebarRoot (regular, Mac) Overview · Check-in · Accounts (groups ▸ accounts) · Plans… · Library…
         └─ Features/<Feature>/<Name>Screen      ← your code
               reads and edits through the stores in the environment
Stores (@Observable, @MainActor)
 LibraryStore ─ LibrarySync (CloudSync actor) ─ LibraryFolder (Storage) ─ files
 PriceStore   ─ PriceService (Prices)
 CheckInStore ─ CheckInSummary (Tracker), the open check-in's date and prices
 PlanStore    ─ PlanEngine (PlannerPlanEngine: the Planner)
 WidgetStore  ─ GlanceSnapshot (Glance) → App Group ← CanIRetireYetWidgets (WidgetKit extension)
 AppPreferences · AppNavigation
```

**Rules so we don't collide:** feature code lives in its `Features/` folder. Replace the body of your placeholder screen, keep its **name and initializer** (the navigation creates it), and add files next to it. If you need something in a store, the design system or the charts, prefer an extension in your feature folder; if it must change a shared file, keep the change small and additive.

Keep math out of the app: it goes in the package (the Planner for the plan, Progress and Trends, Tracker for history and the charts' values, Glance for the widgets), where `swift test` and Linux CI test it. The app keeps the words, the views and the stores, and adds words to package types in extensions (see [Checking without Xcode](#checking-without-xcode)).

## Stores

All stores are `@Observable @MainActor` classes created once in `AppModel` and injected with `.appEnvironment(model)`. In a view:

```swift
@Environment(LibraryStore.self) private var library
@Environment(CheckInStore.self) private var checkIn
@Environment(PlanStore.self) private var plans
@Environment(PriceStore.self) private var prices
@Environment(AppNavigation.self) private var navigation
@Environment(AppPreferences.self) private var preferences
```

For a binding, `@Bindable var navigation = navigation` inside `body`.

### LibraryStore — the library in memory, and keeping it in step with the folder

- **State:** `phase` (`.starting`, `.needsSetup`, `.ready`, `.failed(message)`), `library: Library` (the whole library, from Model), `revision` (goes up with every change), `location` (iCloud Drive or this device), `activity` (idle, loading, saving, syncing, moving), `lastSavedAt`, `lastSyncedAt`, `lastError`, `loadIssues` (problems reading hand-edited files) and `issues` (those and the checks across files, `Library.problems()`, worked out again for each revision), `mergedConflicts` / `conflictFailures`, `upgrade` (what upgrading the library's format did, until dismissed), `saveNotices` (files a save copied to backups before replacing them, or kept, because they changed elsewhere or couldn't be read), `readOnlyReason` (`LoadReport.ReadOnlyReason`: a newer app wrote the library, or its `library.json` can't be read) and `isReadOnly`, `isICloudAvailable`, `openingFailedWithoutICloud` (the failure screen then offers *Start a New Library on This Device*), `isRelocating` (being opened or moved), `canEdit`.
- **Derived:** `valuator` (a `Tracker.Valuator`, rebuilt only when the library changes), `asOfDate` (latest check-in, or today before the first one or when the latest is in the future), `account(_:)`, `sortedPlans`, `mainPlan`, `baseCurrency`, `settings`, `newAccountID(for:)`, `newPlanID(for:)`, `newInstrumentID(for:)` (these skip the IDs of files that failed to load, `unloadedFiles`).
- **Editing:** everything goes through `update(_:)`, which changes a copy, replaces `library` at once and writes only the files that changed in the background, one save at a time. `commit(_:)` does the same and waits for the write, throwing `.saveFailed` if it didn't land. They throw `LibraryStoreError.readOnly(reason)` / `.notLoaded`, and `.busy` while the library is being opened or moved; a failed write shows in `lastError` (an alert over the whole app, `AppPresentation` in `RootView`, and `LibraryStatusBanners`) and reloads what's on disk. Each write is merged with the file on disk (PLAN.md, "Merging, saving and undo"): a change that arrived from elsewhere and wasn't reloaded yet is kept (history record by record) or copied to `backups/` before it's replaced, and listed in `saveNotices`.

  ```swift
  try library.update { $0.accounts[id]?.name = newName }
  try library.upsert(valuation)
  try library.closeAccount(id, on: date, successor: other)
  ```

  Helpers (`LibraryStore+Editing.swift`): `save(_ account:)`, `closeAccount`, `reopenAccount`, `deleteAccount(_:) async` (with its valuations and trades, and clears references to it: successors, plans' excluded accounts and contributions, import profiles' matches and columns; in one `commit(backingUpAs: "delete-account")`), `save(_ instrument:prices:fxRates:)` (a new instrument with its first price), `deleteInstrument` (refused while a valuation or a trade refers to it: `Library.refersTo(instrument:)`), `removeValue(_:)`, `removeTrade(_:) async` (in one `commit`), `upsert(prices:fxRates:indices:)`, `insertMissing(_ fill:) async` (*Fill In Past Prices*: adds only the records the library doesn't have by then, in one `commit(backingUpAs: "fill-history")`; `FetchedPrices.merge(into:policy: .keepExisting)`), `save(_ plan:)`, `deletePlan` (keeps its projections), `duplicatePlan`, `setMainPlan`, `saveBaseline(_:for:)`, `deleteBaseline(_:of:) async` (removes its file; in one `commit(backingUpAs: "delete-baseline")`), `record(_ headline:for:)`, `updateSettings`, `save(_ profile:)`.
- **Backups:** `backups()`; `commit(backingUpAs:_:)` is `commit` with exactly the files the edit changes backed up first, into `backups/<timestamp>-<label>/`, in the same queued operation, and the files as written recorded in the backup after (the import uses it); `undo(_:safetyLabel:)` undoes such an edit and no later one, returning what it left in place (`UndoReport.keptChanges`); `restore(_:)` (*Restore…* in Sync & backups) copies the files as they are now to a `restore` backup, then puts a backup's files back as they were, over later edits; it refuses a backup of another format version, and while the library is read-only, any backup but one with a copy of an unreadable `library.json`.
- **Opening:** `start()` at launch (an existing iCloud library wins, then a local one, else onboarding; iCloud is asked and given a few seconds, so a new device doesn't create a second library), `createLibrary(in:settings:)`, `open(_:)` and `moveToICloud()` (both wait for the queued saves and refuse edits meanwhile; a move is refused when iCloud reports a library there, even one not downloaded yet, or an item to move is already there), `useLibraryOnThisDevice()` (only offered when iCloud Drive isn't available) and `useICloudLibrary()` (Settings → Library, back to the library in iCloud Drive; the one on this device stays), `reloadAll()`, `refreshFromDisk()` (reloads files whose modification dates changed; the root view calls it when the app becomes active), `waitForPendingWrites()`.
  - **Downloading first.** `open(_:)` downloads a library in iCloud Drive before reading it, with the location's `CloudSync.UbiquitousLibraryDownloader` (`makeDownloader()`): every missing file is asked for at once, so reading never waits on the network file by file. While a download has to wait, `phase` is `.starting` (also when onboarding finds a library), so the opening screen shows it. A download whose stream ends without completing goes on to reading.
  - **`opening`** (`LibraryOpening`, Foundation only): the step (`.looking(kind)`, `.downloading(LibraryDownloadProgress)`, `.reading`), `isICloud`, `isStalled`, and the words: `title` ("Downloading 12 of 150 files from iCloud Drive…"), `detail` (bytes), `failureNote`, `fractionCompleted` (the bar), `stalledTitle`, `stalledMessage`, `stalledReasons(onMac:)`. It's stalled after `LibraryStore.openingStallTime` (20 s) without progress (CloudSync's `StallDetector`; a download's progress counts when `hasAdvanced(since:)`).
  - **Stalled:** `keepWaiting()` asks iCloud again for what hasn't arrived and waits another 20 s; `start()` again (Try Again) overtakes the attempt in progress: every attempt has a number, an overtaken one stops its download and drops its results. Neither ever creates a library.
  - **Log:** each step goes to `CloudSync.LibraryLog` (`os.Logger`, subsystem: the bundle id, category `library`): the location, iCloud's answer, the file counts, downloads asked for and failed, the load's files and time, errors. In Console, filter on the category `library`.
- **Sync:** files changed by the other device or a text editor are reloaded automatically, including a change that landed while the library loaded (only those files' entities are replaced, and never a file with an edit waiting to be saved: that save merges the file and reloads it), and a reloaded `library.json` sets `readOnlyReason` as loading it does (read-only while it can't be read, editable again once it's fixed); sync conflicts are merged record by record and listed in `mergedConflicts`. Show them with `LibraryStatusBanners()` or link to `SyncScreen`.
- **Upgrades:** opening a library written in an older format upgrades it (Storage's `Migration.all` and `MigrationReport`), after a backup. `upgrade` (`LibraryUpgrade`, Foundation only: the steps, the notes on what to check, the backup's folder, and the banner's words) keeps the report until `dismissUpgrade()`: `LibraryStatusBanners` says "Your library was upgraded" with *Show details*, which opens `LibraryUpgradeSheet` (`Features/Library/`); closing it dismisses the banner. An upgrade runs once, so it's shown once.
- `LibraryStore.inMemory(library)` holds a library without files (previews, tests). `LibraryStore.needingSetup(in:preferences:)` has no library yet, so onboarding shows, and creates one on this device in the folder given (first launch's screen tests).

### PriceStore — prices, FX and inflation

`fetch(for:on:refresh:) async -> FetchedPrices` (what a check-in needs for what the library holds, `PriceService.needs(for:on:)`; never throws: each item has a `PriceResult` with a readable reason when it failed; a past date its provider has no price for comes from the provider's next route, e.g. gold from `GC=F`, and the result's `shownOrigin` says so), `quote(_ instrument:baseCurrency:on:) async -> FetchedPrices` (one instrument's price and its currency's rate, as records that can be saved: the editor's *Test price fetch*), `fetchEach(_ needs:received:)` (several fetches at once, each result handed over as it arrives, after clearing the session's cache once: *Update Prices*), `pastPriceNeeds(for:) -> PriceNeeds` (what *Fill In Past Prices* would fetch; works in previews too), `fillPastPrices(_:in:progress:) async -> FetchedPrices?` (fetches it, a range per instrument at a time, with each step's progress; `nil` in previews), `canFetch` (false in previews). All of them go through `PriceService.fetch(_:in:refresh:progress:)`, and every save of what they fetched follows one rule, `Library.mergeOutcome(of:policy:)` (docs/PLAN.md, "Prices and FX"). Whether an instrument's prices are fetched is `PriceNeeds.isFetched(_:)`, as in the check-in; no price source needs a key.

Prices are saved outside a check-in by the Instruments screen (`Features/Accounts/InstrumentPriceUpdate.swift`): `InstrumentPriceUpdatePlan` (the held instruments with a price source and their currencies, and the months missing of the library's inflation indices, `PriceStore.indices(for:)`), `InstrumentPriceUpdate` (a line per instrument, rate and index; `settle(in:replacingTyped:)` decides what to save against the library as it is, keeping prices and rates typed in by hand for the date, and adding only index months the library hasn't any value for) and `InstrumentPriceUpdater` (fetches with `fetchEach`, saves with one `upsert(prices:fxRates:indices:)`).

*Fill In Past Prices* (`Features/Accounts/PastPriceFilling.swift`, views in `PastPricesViews.swift`): `PastPricePlan` (a `PastPriceLine` per instrument, rate and index with its dates, and later its `PriceResult`; `offers(among:library:)` for the import's Done step), `PastPriceFiller` (`prepare`, `run` with `PriceStore.fillPastPrices`, then `LibraryStore.insertMissing(_:)`; `phase`, `statusText`, `reset`), `PastPriceText` (ranges, counts, "gold-api.com · XAU back to Sep 2026, Yahoo Finance · GC=F (history) before") and `OldPriceNote` (the note under a chart, from Tracker's `Valuator.oldPrices`). `PastPricesSheet` is presented with `.pastPricesSheet(isPresented:)` from the Instruments toolbar, `ImportDoneStep` (for `ImportReceipt.importedInstruments`), and `OldPriceNoteView` under the charts of `AccountDetailScreen` (`AccountDetailData.oldPrices`) and the Overview (`HistoryChartData.oldPrices`).

### Trade history

Accounts that record trades (docs/TRADES.md; UI.md, "Trade history") have their own pieces in `Features/Accounts/`:

- **Logic** (Foundation only): `TradeListData.swift`: `TradeTypeDisplay` (names, icons, and the filter's `order`), `TradeWording` (a trade's `title`, "Buy 10 VWCE", its `price` in its own currency, "134,75 €", and the list's `subtitle`, "at 134,75 € · 12 Aug 2026 · note"), `TradeList` (an account's trades by month, newest first, with `TradeListFilter` by instrument and type), `TradeHoldings` (from `Valuator.holdings(of:on:)` and `tradeCash(of:on:)`: each `AccountHoldingRow` with its `averageCost` and `share`, then cash and the total), `TradeIncomeYear` (the ledger's `summary(for:)` by year, in the account's currency) and `TradeIssueNote` (`Valuator.tradeIssues(for:)` and `reconciliation(of:)` in words; a trade outside the account's dates offers *Edit Account…*, its only `TradeIssueAction`). `AccountDetailData` carries `tradeHoldings`, `incomeYears`, `tradeIssues` and, in place of `valuations`, `statements` (`AccountStatementRow`: the values whose cash differs from the trades, from `Valuator.tradeFlows`' residuals, with `cashDifference`, or that list positions, with `mismatchCount` from `Valuator.reconcile(_:)` and `positionsText`); its `latest` is the Valuator's snapshot and its new-money ticks the trades' flows. Its `sections` (`AccountDetailSection`) are what the page shows between the chart and the details, in order, on iPhone and the Mac alike. `TradeEditNotes` words what deleting a trade brings in. A `TradeListItem`'s `amount` is what the trade paid or brought in, and its `settlementLabel` marks one paid from outside the account.
- **Views**: `TradeViews.swift` (`TradeHoldingsRows`, `TradeHoldingsGrid` on the Mac, `TradeListRowView`, `TradesTable` on the Mac, `TradeFilterMenu`, `TradeIncomeYearView`, `TradeIssueBanners`). Trades are only imported or deleted (`LibraryStore.removeTrade`), never typed.
- **New accounts**: a brokerage, crypto or metals account records trades (`AccountForm.valuationMode`, the kind's `defaultValuationMode`; no choice to make). Its trades come from an import.
- **The Overview**: *Needs attention* has an item per account whose trades have problems, opening it (`OverviewAttention.tradeProblems`: "Directa: 2 problems with trades", counting the same `TradeIssueNote`s as its page).
- Everything that reads what an account holds uses `Valuator.snapshot(of:on:)`, `holdings(of:on:)` or `firstRecordDate(of:)`, never a valuation's `positions` (for a trades account those are only a statement to check).

### Account values

How the app reads an account's values (UI.md, "Account detail"); the logic is in Tracker and `Features/Accounts/`, Foundation only.

- **Own currency.** Tracker's `ValueCurrency` (`.base`, `.account`) picks the currency of `Valuator.value(of:on:in:)`, `series(of:in:grid:from:through:)` and `change(of:from:to:in:)`. In `.account` a dollar account is worth its dollars and needs no exchange rate (only positions priced in a third currency do). `AccountDetailData` shows the value, change, chart and values in the account's currency (`currency`, `amount`, `history`), with `baseValue` (`AccountBaseValue`: `.known` at the day's rate, or `.rateMissing`) under the value; list sparklines use it too. Net worth, subtotals and the sidebar stay in the base currency.
- **Missing values.** Tracker's `MissingValues` says what values lack, from `Valuator.missingValues(of:on:in:)` and `missingValues(in:on:)`: its `gaps`, each a missing price or rate, or an open account without a value (`Gap`: the item, the accounts it leaves incomplete, the dates). Charts draw an incomplete point as a gap in an account's line (`[ChartPoint].completeRuns`, `isolatedPoints`) or a dashed, grey stretch of a total (`segments`), or dashed lines along stacked areas (`StackedAreaData`), never as zero. `MissingValueNote` (`PastPriceFilling.swift`) words the note under a chart, with *Fill In Past Prices…*: `account(chart:netWorth:name:)` from `AccountDetailData.missing` and `missingBaseRates`, `overview(_:accountName:instrumentName:)` from `HistoryChartData.missing`; `OverviewAttention.pastGaps` makes the *Needs attention* items.
- **What each kind records** (docs/ACCOUNTS.md): values come only from imports, and the account's page shows them read-only. A value is deleted from its row (`LibraryStore.removeValue`), and `AccountValueNotes` asks to check the money in and out of the value after it.
- **Money in and out.** A cash or savings account's `AccountValuationRow`s carry `flow`, what they saved (Tracker's `Valuator.flow(of:previous:)`), and `moved` (`Valuator.moved(_:previous:)`: saved − money in + money out, the money moved between your own accounts, worked out and never stored), and `AccountDetailData.valuationsShowMoneyInOut`, `valuationsShowInterest` and `movedNote` say what the list shows (docs/ACCOUNTS.md, "Moved between your accounts").
- **Empty accounts.** An account that holds nothing (`Valuator.emptySince(of:on:)`: a zero balance, or no cash and no quantity) has nothing to check in, so it's never stale (`AccountStaleness.stale`, `AccountListData.swift`): not in the list, the sidebar, the detail or *Needs attention*. Once it's been empty for longer than the staleness threshold, `AccountStaleness.emptySince` (`AccountDetailData.emptySince`) makes its page suggest closing it on that day.

### CheckInStore — the open check-in

Holds the open check-in's `date` and its fetched `priceList`; nothing is kept on the device and nothing is typed in. The values come from imports, which write as they always do (`ImportScreen(checkIn:close:)`).

- `begin(on:)` opens it on the date given, the open one, or the suggested date (Tracker's `CheckInDates`), and fetches prices for what the library holds (unless turned off in Settings). `fetchPrices(refresh:)` fetches again; the screen calls `begin()` after each import. `cancel()` drops the date and the prices.
- Read: `summary` (Tracker's `CheckInSummary`: net worth on the date with the fetched prices, the change since the previous check-in, and the `updated` and `notUpdated` accounts: those with and without a record in the date's month), `priceList` (every instrument, rate and index with its source or failure), `isFetchingPrices`, `status` (for the accessory: `CheckInStatus` with `summary()`, `isDue`, `isOpen`, `isActive` (either), `nextCheckIn`).
- `save() async throws -> CheckInSaveResult` writes the fetched prices, FX rates and index values in one `LibraryStore.commit` (a price typed by hand for the date stays) and waits for the files. Then it starts the main plan's run for this month's answer with `PlanStore.recordCheckInAnswer(on:)`, without waiting for it: the confirmation follows `PlanStore.checkInAnswer` (its progress, then the headline). Only the library's latest check-in does: a past one (`CheckInStore.laterCheckIn(than:in:)`) records no headline and no baseline, and returns `result.laterCheckIn` (`isPast`). Without an open check-in it throws `CheckInStoreError.noCheckIn`.

### PlanStore — runs on request, progress, results and whether they're out of date, headlines, baselines

The numbers come from a `PlanEngine` (see `Stores/PlanEngine.swift`): `run(_:progress:)` (a `PlanProgressHandler`, if any, told where the run is, as a `PlanRunProgress`: the `mode`, and the Planner's `PlannerProgress` once it reports — its `phase`, `.earliestAge`, `.simulating`, `.sustainableSpending`, `.assetsNeeded`, `.agesWithout` or `.summarising`, `completed` / `total` in the phase's unit, the whole request's `fraction`, the scanned `ages` — or none before, `.starting`) and `cachedResults(for:)` (results already computed for exactly that request, without running; `nil` by default). The app uses `PlannerPlanEngine` (`Stores/PlannerPlanEngine.swift`): `Planner.run`, its `PlannerProgress` passed on (a request that needs two runs, a what-if's saving or a focus age, shares the bar between them), results cached per plan, library inputs, kind, focus age and start date. Previews use `PreviewPlanEngine` (`Preview/`: made-up years run through the same mapping as a Planner run, made-up details, and with a handler made-up progress through the phases, over about 20 × its `delay`).

**Nothing runs on its own.** Screens call `run` only from a button (Calculate, Recalculate ⌘R, Run What-If) or for something the user asked for that needs results (Save Baseline; turning on the Overview's *Future* when the main plan has no results). The one exception is a check-in recording its month's answer (caught up at the next launch if the app was closed first). There's no `scheduleRun` any more: opening a plan, editing it, moving a slider or choosing another age makes results out of date instead.

- `run(_ plan:_ kind:mode:) async -> PlanResults?` runs off the main thread and cancels the previous run of the same plan and kind, or joins it when the request is the same, also a check-in's run of the plan. The kind (`PlanRunKey.Kind`) is `.base`, the plan as it is; `.whatIf`, with the plan's what-if (`mode: .fast` for its quick estimate); `.focus`, the charts at the plan's focus age; or `.checkIn`, whose results are the plan's own. `cancel(_:kinds:)` (by default the Plan screens' runs, never a check-in's), `isRunning(_:)`, `isRunning(_:_:)`, `running`, `errors`.
- **What if and focus age:** `whatIf(of:)` and `focusAge(of:)`, each plan's what-if (`PlanWhatIf(retirementAge:retiredSpending:monthlySaving:equityReturn:)`) and chosen age, so switching plans and coming back keeps them (not saved); `setWhatIf(_:for:)` (an empty one throws the what-if's results away and stops its run) and `setFocusAge(_:for:)` (`nil` throws the other age's results away). The Plan screen's `PlanSession` reads and sets them here, never a copy.
- **Progress:** `progress` (by `PlanRunKey`) and `progress(of:_:)`, the `PlanRunProgress` of each run in progress, set to `.starting` when it starts, updated at most about ten times a second (an update that would move the bar back is dropped) and cleared when it ends.
- **Out of date:** each plan's latest results of each kind are kept in one table with their `PlanRunBasis` (a `PlanSlot`): the plan, `PlanRunInputs` (the library data a run reads), the start date, mode, what-if and focus age. `staleReasons(of:_:plan:)` compares it with the plan (pass the session's unsaved draft), the library as it is now and the plan's what-if and age, giving `PlanStaleReason`s: `.plan` (not a rename), `.library`, `.whatIf`, `.focusAge`. `lookUp(_:_:modes:)` takes results the engine kept for exactly the current inputs, without running. A run that finishes after an edit keeps its basis, so it shows as out of date.
- `results(of:_:)`: the Planner's `PlanResults` (`Sources/Planner/Results`, made from a run by `PlanResults(result:mode:birthDate:computedAt:)`) — `headline: RetirementAnswer` (the Model's; earliest age and date, confidence, success today and at the target age, sustainable spending, readiness), `successByAge`, `portfolio` (fan), `markers`, `income`, `taxes`, `spending`, what a baseline saves (`start`, `accounts`, `years`), `currency` (the base currency when they were calculated, which every amount is in: results in another currency than the library's, calculated before it changed, aren't returned, so the plan is calculated again), and `details` from the Planner (plan hash, ages, what retiring today needs, the run's warnings, the focus age's details with its bridge failures, and `headline`, the record written at a check-in, identical to the CLI's). All plain values that feed the chart components directly.
- **The answer:** `latestAnswer(of:)`, the Planner's `LatestAnswer`, the one place the answer shown is picked: the plan's latest results (`latestResults(of:)`: its `results`, unless a check-in recorded a newer answer since the date they start from), or its last recorded headline, as a `RetirementAnswer`. `mainAnswer` is the main plan's, for the Overview, Progress and the widgets, and `mainHeadline` its `answer`. Never starts a run.
- **Kept on the device** (UI.md, "Calculating"): `archive`, a `PlanResultsArchive` (`Stores/PlanResultsArchive.swift`; `AppModel.live()` passes `PlanResultsArchive.standard()`, `Caches/<bundle id>/PlanResults`; `nil` in previews), gets each plan's own results after every run (`.base` and a check-in's, not a what-if's or a focus age's), with what they were calculated from: the plan, a fingerprint of the library data the run read (`PlanRunInputs.fingerprint`, FNV-1a of its sorted JSON), the start date, mode and engine version. One folder per library (a hash of its path), one file per plan, written off the main thread in order. `restoreKeptResults()` (`AppModel`, once the library is loaded, before `recordMissingCheckInAnswer`) shows them again once per library: results this session already has win; a different fingerprint gives a basis without `inputs`, so they're out of date with `.library`; an edited plan gives `.plan`; ones with the same inputs also go back to the engine (`PlanEngine.remember(_:for:)`, a no-op by default; `PlannerPlanEngine` puts them in its cache). Files of another format or engine, unreadable ones and those of plans the library no longer has are deleted. A library's folder is named by its path in the app's home when it's there (`libraryKey`): a library on the device is in the app's container, whose full path changes each time the app is installed again (a run from Xcode) or updated. What happens is logged (category `plans`, `PlanResultsLog`): kept, restored up to date or out of date and why, or dropped and why. `PlanResults` and what it holds are `Codable` for this (the Planner's `PlanIssue`, `PlanSection`, `AssetsNeeded`, `AgeWithout` and `AgeCount` too); non-finite doubles are written as strings.
- `recordCheckInAnswer(on:)` starts the main plan's run for a saved check-in (kind `.checkIn`, which the Plan screens join but don't cancel) and returns at once, asking iOS for background time until it's written (`BackgroundActivity`); `checkInAnswer` (`CheckInAnswerRun`: date, plan, `isRunning`, then `headline` or `error`) is what the confirmation follows. `checkInSaved(on:) async` is the run itself: it records the headline (`projections/<plan>/headlines`), saves the yearly baseline at the year's first check-in and waits for the writes; what can't be saved shows in `LibraryStore.lastError` (`reportError(_:)`). `recordMissingCheckInAnswer(today:)` (`AppModel`, once the library is loaded) records the latest check-in's answer when no headline on or after it is recorded, e.g. the app was closed first: once per plan and date while the app runs. `saveBaseline(for:label:kind:on:)`, `recordedHeadlines(for:)`.

### WidgetStore — the widgets' snapshot

`Features/Import/`: one flow for spreadsheets and broker exports. `ImportFlow` (plain values) holds the file, the mapping, the preview, the user's decisions and the step; `ImportController` (`@Observable`) does the writing: `runImport(in:)` applies the preview with `LibraryStore.commit(backingUpAs: "import")` (`ImportPreview.apply(to:)`), `undoImport(in:)` undoes it with `LibraryStore.undo`, and `saveProfile` writes `imports/<id>.json`.

## Design system

- **Colours** (`Palette`, backed by colour sets in `App/Resources/Assets.xcassets`, light and dark): the asset-class colours in stacking order (`Palette.color(for: assetClass)`: cash blue, bonds orange, equity aqua, gold yellow, crypto magenta, real estate green, other violet, debt red), the categorical `series` slots in fixed order, `accent` (the one hue for everything else), `ink` (actual history and text), `secondaryInk`, `mutedInk`, `gridline`, `axis`, `positive` / `negative` (changes, always with a sign and arrow; `change(_:)` by direction), status colours (`good`, `warning`, `critical`; always with an icon and a label), surfaces (`page`, `card`, `border`). Charts name colours by role with `ChartColor`: `Palette.color(for:)` for washes and fills, `Palette.stroke(for:)` for lines, the edges of stacked areas and small marks (legend swatches, dots, the allocation bars); the roles resolve in `Components/Charts/ChartSupport.swift`, the asset classes in `Palette.swift`, which the widgets compile too. In light mode the stroke of orange, aqua, yellow and magenta is a darker step of the hue (`seriesStroke`, colour sets `Series…Stroke`), so every line reaches 3:1 on the card and on the page; in dark mode it's the colour itself. Validate any colour change with the dataviz skill's `validate_palette.js`, light and dark.
- **Spacing:** `Metrics` (`xs` 4, `s` 8, `m` 12, `l` 16, `xl` 24, `cardRadius`, `lineWidth`, `barRadius`, `readableWidth`). Icons: `AccountKind.systemImage`, `AccountGroup.systemImage`, `AppSymbol`.
- **Numbers** (`AmountFormat`, locale-aware): `amount(_:currency:precision:)` (`.whole` by default, `.cents` in check-in fields and account detail, `.automatic`), `signedAmount`, `percent`, `number`, `compact` (`312k`, `1,2M` for charts; `compact(_:step:)` with the decimals an axis's ticks need), dates (`shortDate` "30 Sep", `shortDate(_:relativeTo:)` "30 Nov 2021" outside this year, `mediumDate`, `longDate`, `monthName`). Zero never has a sign: an amount that rounds to it reads `0 €`, and `DeltaFormat` gives `DeltaText` no arrow for it. Model's `Decimal.doubleValue` for charts only; back the other way, a planner or chart `Double` becomes a whole number with `Decimal(wholeNumber:)` or `Int(wholeNumber:rounding:)` (Model's `WholeNumber.swift`), never `Int(_:)`, which traps on NaN, an infinity or a value beyond `Int`'s range (they give 0). **Quantities and unit prices** (`QuantityFormat`, the same everywhere): `quantity` (up to 8 decimals, trailing zeros trimmed), `unitPrice(_:currency:)` (the currency's symbol, 2 decimals from 1 up, 4 significant digits below: `0,004312 €`), `labelled(_:_:)` (a label and its value in one text, so they wrap together), `unit(_:)` ("sh" for shares); a holding's lines are `AccountPositionText`'s (`Features/Accounts`). Model's `CalendarDate.dateValue` gives a `Date` (noon, local time).
- **Words:** counts and lists are Model's `Wording`, as the CLI and the other modules write them: `Wording.count(2, "account")` "2 accounts", `Wording.list(_:)` "A, B and C" (and the design system's `Wording.names(_:)`, which lists a repeated name once); `capitalizedFirst` starts a sentence. Months are Glance's `GlanceText`, as the widgets write them: `month(_:relativeTo:)` "May", or "May 2025" outside that year, `monthAndYear` "April 2042", `shortMonth` "Apr" (also relative to a date), `shortMonthAndYear` "Apr 2042"; and the confidence as "9 of 10", `futures` and `inSimulatedFutures`.
- **Input:** `AmountInput.decimal(from:locale:)` reads `1.234,56`, `1234.56`, `0,4215` and `−240`, and `AmountInput.parse(_:locale:)` tells an empty field from one that can't be read (the account and price forms, and the plan's `PlanNumberText`); `AmountInput.text(for:)` fills a field. `CurrencyChoices` and `CountryChoices` for pickers, with `including(_:)` putting the current value first when it isn't one of them (also for kinds: `AccountKind.knownValues.including(kind)`).
- **Views:** `AmountText(amount, currency:, precision:, signed:, short:, tabular:, animatesChanges:)` — tabular figures, `.privacySensitive()`, so it draws as a placeholder while amounts are hidden (see [Hiding amounts](#hiding-amounts)); `signed` always shows the sign, without colour (a trade's cash); `short` shows `300.000 €`, `12,3M €`, `1,00B €` (Glance's `ShortAmount`) for a chart's callout, and VoiceOver reads the full amount. `DeltaText(amount)` / `DeltaText(percent:)` — ▲/▼, sign and colour; a change in money hides with the eye, one in per cent stays. `Card("Title") { … }`, `Card { … } header: { SectionHeader("Title") { accessory } }`. `StatusBanner(.info/.success/.warning/.error, title, message:, actionTitle:, action:)`. `LibraryStatusBanners()` shows an upgrade of the library's format, read-only (and why), save errors, unreadable files and merged conflicts. `.sheetTitle("Title") { dismiss() }`: a sheet's title, inline on iPhone and iPad, and its *Done* button.
- **Editing sheets keep what's typed:** each compares its form with the one it opened with (the forms are `Equatable`) and passes that to `.interactiveDismissDisabled(_:)`, so swiping the sheet down does nothing once something changed and only *Cancel* discards it (`NewAccountScreen`, `EditAccountSheet`, the instrument editor, `PlanItemEditor`). Pushed, `InstrumentEditor` hides the back button while there are changes and shows *Cancel* and *Save* instead.
- **Mac layouts:** a Mac window can't be smaller than the minimum size of its content, so every page's content scrolls (a `ScrollView`, a `List`, a `.grouped` `Form`, or a `Table` that is the whole page), and the window opens at 1200 × 800 with a minimum of 900 × 600 (`CanIRetireYetApp`). That minimum is fixed, never measured through the pages (`FixedMinimumSize`): their minimums move as they lay out (a `ViewThatFits`, a chart fitting its ticks to its width), and AppKit stops a window whose constraints never settle ("needing another Update Constraints in Window pass"). The split view measures its columns the same way, so a column whose content's minimum can move gets a fixed one too: `.fixedMinimumSize(width:height:)` (the Mac only; the Plan screen's page, 320 × 300, beside which What if is a column of its own width that scrolls). Content pinned above or below a scrolling area goes in `OverflowScrollView(maxShare:) { … }`: its own height while that fits, at most that share of the height it's offered, scrolling beyond, never a minimum height (the import's column settings). Content that never scrolls, above all text with `.fixedSize(horizontal: false, vertical: true)`, which is measured at the narrowest width, makes the window taller than the screen. A table on a scrolling page is a `PageTable` (Mac, and iPad): column titles and a line per item, as tall as its lines, with click to select, double-click to open and a context menu; each column is a `PageTableColumn` (a minimum and a maximum width) so the lines line up. Pass `selection:` to keep the selected line yourself (the plan debugger shows the chosen year in detail below its table). Not a `Table`, which scrolls on its own and needs a guessed height. The account's values and trades use it on the Mac, the plan debugger on the Mac and iPad.
- **Environment values:** `\.baseCurrency`, set by `appEnvironment`; `AmountText` reads it, so you rarely pass a currency. `\.chartSurface` is what a chart draws the gaps between stacked areas in: the card, or `Palette.page` for the Overview's history chart. Whether amounts are hidden is `\.redactionReasons` (see [Hiding amounts](#hiding-amounts)); whether a feedback screenshot is being taken, `\.hidesPersonalData` (see [Feedback](#feedback)).

## Hiding amounts

The eye button, ⌘⇧H, the check-in's banner and "Hide amounts when the app opens" set `AppPreferences.hidesAmounts`; while it's on, `appEnvironment` redacts each scene for `.privacy` (`.redacted(reason:)`), so SwiftUI draws a placeholder for every view marked `.privacySensitive()`, and names, dates and labels stay readable. It's SwiftUI's redaction, the same as the widgets' on a locked device and a feedback screenshot's (see [Feedback](#feedback)); the app-switcher cover (`PrivacyCover`) is a separate setting. The pieces are in `Shared/`, which the widgets compile too:

- **Asking:** a view reads `redactionReasons.hidesAmounts` (`.privacy`), for what VoiceOver reads and for the charts' relative axis; nothing else needs to know.
- **An amount on its own:** `AmountText`, `DeltaText` and `CheckInPlainAmount` are `.privacySensitive()` and read "Amount hidden" to VoiceOver; any other figure, a quantity or a table cell, gets `.privacySensitiveAmount()`, which does both. It hides wherever it sits, also inside a view marked `.privacySensitiveInFeedback()` (see [Feedback](#feedback)): the marks only ever add hiding, so never wrap an amount in `.privacySensitive(false)`.
- **A sentence with amounts in it:** an `AmountSentence` ("You saved \(amount: saved) and markets added \(amount: markets)."): words, and amounts kept apart, built with `\(amount:)` in a string literal, `+`, `joined(separator:)` and `listed()`. `AmountSentenceText(sentence)` draws it as one text that wraps; while amounts are hidden `AmountPlaceholderRenderer` (a `TextRenderer`) draws a bar in place of each amount (`AmountRun`), the amounts are clear in case no renderer draws, and VoiceOver reads "amount hidden" there (`spoken(hidesAmounts:)`). The plan's and Progress's words (`PlanWords`, `PlanMilestoneText`, `PlanProgressText`, `PlanChapterStory`), the check-in's (`CheckInWording`), a holding's (`AccountPositionText`, `QuantityFormat.quantitySentence`, `labelled(_:amount:)`) and the trades' (`TradeWording`) return them. A sentence is never `.privacySensitive()`: that would hide its words too.
- **Charts** keep their shape, and their value axis shows multiples of a base (`AmountAxisTicks`; see [Charts](#charts)): the one label of the person's data left unredacted (`.unredacted()`), since it reveals no amount; a feedback screenshot hides it too (see [Feedback](#feedback)). Every other amount label is `.privacySensitive()`.
- **Fields** you type into aren't marked: they show what you type, as the check-in's banner says.

## Widgets

`Widgets/` is the `CanIRetireYetWidgets` extension (WidgetKit, iPhone, iPad and Mac), embedded in the app. It links `Model` and `Glance` only, and compiles in the app's `AmountFormat.swift` (amounts read the same), `Palette.swift` (the same colours, from the asset catalog's colour sets) and `Shared/` (`AppGroup.swift`, `ReadinessRing.swift`, and `AmountSentence` and `AmountRedaction` for hiding amounts).

- `GlanceProvider` reads the snapshot (`AppGroup.snapshotURL`, `GlanceFile.read(at:)`) and makes a timeline entry for now and each of the next seven midnights, since the countdowns change with the day; the numbers only change when the app writes a new snapshot, which reloads the widgets. The gallery and placeholders get `GlanceSnapshot.placeholder(today:)`, made-up numbers (the mockups') around today.
- One `Widget` per row of UI.md's table (`CanIRetireYetWidgets`, the bundle): `RetireInWidget`, `NetWorthWidget`, `SinceCheckInWidget`, `ReadinessWidget`, `CheckInWidget`, `EarliestAgeWidget`, `SpendingWidget`, `AllocationWidget`, `MilestoneWidget`, each in `RetirementWidgets.swift`, `NetWorthWidgets.swift`, `CheckInWidget.swift` or `MilestoneWidget.swift`. - Their words: `AnswerWords`, `ReadinessWords` (Glance's `ReadinessFigure`, which the Overview's ring shares: "58%", "58%+", "<5%", below 100% rounded down, as the app shows it), `NetWorthWords`, `CheckInWords`, `WidgetMoney` (`AmountFormat` and `DeltaFormat`), and Glance's `GlanceText` and `RetirementCountdown`. ## Feedback

Debug builds (the `FEEDBACK` compilation condition, set for the Debug configuration in `project.yml`) include in-app feedback with [FeedbackKit](https://github.com/j23n/feedbackkit): shaking the iPhone or iPad, taking a screenshot (a banner offers it), Help › Send Feedback… or Settings › Feedback opens a form with a screenshot of the window, which Quick Look's Markup can annotate on iPhone and iPad. The report goes to the owner's private inbox, [j23n/feedback](https://github.com/j23n/feedback), where it's triaged before an issue is filed here; the screenshot never leaves the inbox.

- **The screenshot hides only the person's data.** FeedbackKit's `.privacySensitiveViews` redaction (`AppEnvironment`, on both windows): while `FeedbackCenter.isCapturing`, FeedbackKit redacts each window for `.privacy`, as the eye does (see [Hiding amounts](#hiding-amounts)), so SwiftUI draws placeholders for the views marked `.privacySensitive()`, and it paints over the text in text fields and editable text views. `AppEnvironment` also sets `\.hidesPersonalData` (`Shared/PersonalDataRedaction.swift`), which marks the rest of the person's data. The app's own text (labels, section headers and footers, button titles, empty states, the tab bar) stays readable, so a report shows what the person was looking at.
- **Marking a view** that shows the person's data, which every new view must do:
  - An amount, or what's derived from one (a change, a quantity, a price): `AmountText`, `DeltaText` or `.privacySensitiveAmount()` (see [Hiding amounts](#hiding-amounts)). A change in per cent hides in a screenshot too.
  - The rest of the person's data: `.privacySensitiveInFeedback()`, which redacts it (`.redacted(reason: .placeholder)`) only while a screenshot is taken, so the eye leaves it readable. Outside a screenshot it adds nothing and takes nothing away: the eye still hides the amounts inside it. It's never `.privacySensitive(false)`, which would keep them readable. Names they chose or imported (accounts, institutions, instruments and their symbols, plans, chapters, events, baselines, import profiles), their records' dates, notes, the plan's ages and years and its answer, shares of their money, file names and paths, and an import's cells. A label that mixes the app's words with any of these is marked as a whole; `StatusBanner(…, personal: .title / .message)` marks only its texts with the person's data.
  - A sentence: `AmountSentenceText` (and the plan's `PlanStoryText`) draws its words as placeholders in a screenshot too, since they hold names, ages and dates; text around it that isn't part of the sentence stays.
  - Charts are marked as a whole: all their text hides, the relative value axis too, and their lines stay.
  - A navigation or window title with the person's data: `.personalNavigationTitle(account.name, hidden: "Account")`, which reads `hidden` in a screenshot, and on the Mac `.personalNavigationSubtitle(_:)`. SwiftUI's redaction doesn't reach the titles UIKit and AppKit draw.
  - A control the system draws with the person's data (a picker whose choice is an account's name, a date picker with a record's date or the birth date): `.personalControl()`, which marks it and paints over it with FeedbackKit's `feedbackHidden()`.
  - Never mark a view that shows the person's data `.unredacted()`. A view that isn't marked shows in the screenshot, which the person sees before sending it. Alerts and confirmation dialogs are drawn by the system, so their text isn't hidden.
- **Where the app is:** `AppNavigation.feedbackScreen` (the tab or sidebar item, a sheet, the check-in, without account or plan IDs) goes with each report (`Sources/App/Feedback.swift`).
- **Settings › Feedback** turns it off, turns the gestures off, holds the GitHub token (a fine-grained token for j23n/feedback with Issues and Contents read and write, kept in the Keychain) and sends what's waiting.
- Release builds link the package but never create a `FeedbackCenter`: no gesture, no menu item, nothing sent.

## Library location and sync

At launch `LibraryStore.start()` asks `CloudSync.LibraryLocator` for the iCloud container's `Documents/` (off the main thread) or `Application Support/<bundle id>/Library`, remembers the choice on the device, downloads a library in iCloud Drive that isn't all on the device (`CloudSync.UbiquitousLibraryDownloader`: the folder on disk, then an `NSMetadataQuery`, every missing file asked for at once, `LibraryDownloadProgress` until all are here), and loads through `CloudSync.LibrarySync`: coordinated reads and atomic writes (`CoordinatedFileAccess`), an `NSMetadataQuery` watcher that also downloads files eagerly (polling for a local library), and conflict merging with `Storage.ConflictResolver` (`NSFileVersion`). Nothing on that path touches the files on the main thread. A library on this device can be moved to iCloud Drive from Settings. A library written by a newer app, or whose `library.json` can't be read, opens read-only, and the banners say which.

If the iPhone sticks on the opening screen, Console (on a Mac, with the iPhone connected) shows each step: filter on the subsystem (the bundle id) and the category `library`.
