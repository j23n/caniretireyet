# The app

The SwiftUI app for iPhone, iPad and Mac (iOS 26 / macOS 26), on top of the Swift package in the repository root. Read [docs/UI.md](../docs/UI.md) for what it looks like, and this file for how it's built and where your code goes.

Build it on a Mac: `brew install xcodegen && xcodegen generate --spec App/project.yml`, then open `App/CanIRetireYet.xcodeproj`. The project is generated from [project.yml](project.yml) and never committed.

## At a glance

```
CanIRetireYetApp (@main)          one AppModel, injected into every scene
 └─ RootView                      launch · onboarding · main navigation
     ├─ TabRoot (compact)         Overview · Accounts · Plan tabs, check-in in the tab bar accessory
     └─ SidebarRoot (regular, Mac) Overview · Check-in · Accounts (groups ▸ accounts) · Plans… · Library…
         └─ Features/<Feature>/<Name>Screen      ← your code
               reads and edits through the stores in the environment
Stores (@Observable, @MainActor)
 LibraryStore ─ LibrarySync (CloudSync actor) ─ LibraryFolder (Storage) ─ files
 PriceStore   ─ PriceService (Prices)
 CheckInStore ─ CheckInDraft (Tracker), kept in Application Support
 PlanStore    ─ PlanEngine (PlannerPlanEngine: the Planner and the tax registry)
 PrivacySettings · AppPreferences · AppNavigation
```

## Folders

| Folder | What goes there | Owner |
| --- | --- | --- |
| `App/` | `@main`, `AppModel` (creates the stores), environment injection, menu commands | app core |
| `Stores/` | The stores, and the logic they need that isn't UI | app core (PlanStore: Plan engineer fills in the engine) |
| `Navigation/` | Root view, tabs, sidebar, the check-in accessory, sheets, `AppNavigation` | app core |
| `DesignSystem/` | Colours, spacing, number formatting (amounts; quantities and unit prices, `QuantityFormat`), `AmountText`, `DeltaText`, `Card`, `SectionHeader`, `StatusBanner`, `OverflowScrollView`, `PageTable`, input parsing, SF Symbol names | app core |
| `Components/Charts/` | Reusable Swift Charts views and their plain-value inputs | app core |
| `Features/<Feature>/` | One folder per feature, starting with its screen | feature engineers |
| `Preview/` | The made-up library, a made-up plan engine, preview helpers | app core |
| `Resources/Assets.xcassets` (next to `Sources/`) | Colour sets, light and dark | app core |

**Rules so we don't collide:** feature code lives in its `Features/` folder. Replace the body of your placeholder screen, keep its **name and initializer** (the navigation creates it), and add files next to it. If you need something in a store, the design system or the charts, prefer an extension in your feature folder; if it must change a shared file, keep the change small and additive.

Keep logic that doesn't need SwiftUI in files that import only Foundation and the package modules (like everything in `Stores/`): it can then be type-checked and tested on Linux (see [Checking without Xcode](#checking-without-xcode)).

## Stores

All stores are `@Observable @MainActor` classes created once in `AppModel` and injected with `.appEnvironment(model)`. In a view:

```swift
@Environment(LibraryStore.self) private var library
@Environment(CheckInStore.self) private var checkIn
@Environment(PlanStore.self) private var plans
@Environment(PriceStore.self) private var prices
@Environment(AppNavigation.self) private var navigation
@Environment(PrivacySettings.self) private var privacy
@Environment(AppPreferences.self) private var preferences
```

For a binding, `@Bindable var navigation = navigation` inside `body`.

### LibraryStore — the library in memory, and keeping it in step with the folder

- **State:** `phase` (`.starting`, `.needsSetup`, `.ready`, `.failed(message)`), `library: Library` (the whole library, from Model), `revision` (goes up with every change), `location` (iCloud Drive or this device), `activity` (idle, loading, saving, syncing, moving), `lastSavedAt`, `lastSyncedAt`, `lastError`, `loadIssues` (problems in hand-edited files), `mergedConflicts` / `conflictFailures`, `saveNotices` (files a save copied to backups before replacing them, or kept, because they changed elsewhere or couldn't be read), `isReadOnly` (a newer app wrote the library), `isICloudAvailable`, `isRelocating` (being opened or moved), `canEdit`.
- **Derived:** `valuator` (a `Tracker.Valuator`, rebuilt only when the library changes), `asOfDate` (latest check-in, or today), `netWorth`, `planAssets`, `changeSinceLastCheckIn`, `staleAccounts(threshold:)` (never an empty account: see [Account values](#account-values)), `account(_:)`, `openAccounts`, `openAccounts(in:)`, `closedAccounts`, `accountGroups`, `sortedPlans`, `mainPlan`, `baseCurrency`, `settings`, `newAccountID(for:)`, `newPlanID(for:)`, `newInstrumentID(for:)` (these skip the IDs of files that failed to load, `unloadedFiles`).
- **Editing:** everything goes through `update(_:)`, which changes a copy, replaces `library` at once and writes only the files that changed in the background, one save at a time. `commit(_:)` does the same and waits for the write, throwing `.saveFailed` if it didn't land. They throw `LibraryStoreError.readOnly` / `.notLoaded`, and `.busy` while the library is being opened or moved; a failed write shows in `lastError` and reloads what's on disk. Each write is merged with the file on disk (FILE_FORMAT.md, "Saving"): a change that arrived from elsewhere and wasn't reloaded yet is kept (history record by record) or copied to `backups/` before it's replaced, and listed in `saveNotices`.

  ```swift
  try library.update { $0.accounts[id]?.name = newName }
  try library.upsert(valuation)
  try library.closeAccount(id, on: date, successor: other)
  ```

  Helpers (`LibraryStore+Editing.swift`): `save(_ account:)`, `closeAccount`, `reopenAccount`, `deleteAccount` (with its valuations and trades, and clears references to it: successors, plans' excluded accounts and contributions, import profiles' matches and columns), `save(_ instrument:)`, `save(_ instrument:prices:fxRates:)` (a new instrument with its first price), `deleteInstrument` (refused while a valuation or a trade refers to it: `Library.refersTo(instrument:)`), `upsert(_ valuation:)`, `replace(_:with:)`, `removeValuation`, `saveValue(_:replacing:) async` and `removeValue(_:)` (one value outside a check-in: a value before the opening date moves it back, and the next value's automatic flow is worked out again, a typed one kept; Tracker's `Library.saveValue`, `removeValue`, `editValuations`), `addTrade(_:) async`, `updateTrade(_:replacing:) async` and `removeTrade(_:) async` (a trade of a trades account, in one `commit`, returning Tracker's `TradeEdit`: a date before the opening date moves it back, and the automatic new money of later values follows; their previews are `Library.previewAddingTrade` etc.), `convertToTrades(_:) async` and `convertToSnapshots(_:) async` (Tracker's `conversionToTrades(of:)` / `conversionToSnapshots(of:)` applied in one `commit(backingUpAs: "convert-to-trades")` / `"convert-to-snapshots"`, returning the `AccountConversion`), `upsert(prices:fxRates:indices:)`, `insertMissing(_ fill:) async` (*Fill In Past Prices*: adds only the records the library doesn't have by then, in one `commit(backingUpAs: "fill-history")`; `PastPriceFill.insertMissing(into:)`), `save(_ plan:)`, `deletePlan` (keeps its projections), `duplicatePlan`, `setMainPlan`, `saveBaseline(_:for:)`, `record(_ headline:for:)`, `updateSettings`, `save(_ profile:)`.
- **Backups:** `backups()`; `backup(paths:label:)` copies files into `backups/<timestamp>-<label>/` after the queued saves; `commit(backingUpAs:_:)` is `commit` with exactly the files the edit changes backed up first, in the same queued operation, and the files as written recorded in the backup after (the import uses it); `undo(_:safetyLabel:)` undoes such an edit and no later one, returning what it left in place (`UndoReport.keptChanges`); `restore(_:)` puts a backup's files back as they were, over later edits, and refuses a backup of another format version.
- **Opening:** `start()` at launch (an existing iCloud library wins, then a local one, else onboarding; iCloud is asked and given a few seconds, so a new device doesn't create a second library), `createLibrary(in:settings:)`, `open(_:)` and `moveToICloud()` (both wait for the queued saves and refuse edits meanwhile), `useLibraryOnThisDevice()`, `reloadAll()`, `refreshFromDisk()` (reloads files whose modification dates changed; the root view calls it when the app becomes active), `waitForPendingWrites()`.
  - **Downloading first.** `open(_:)` downloads a library in iCloud Drive before reading it, with the location's `LibraryDownloading` (`CloudSync.UbiquitousLibraryDownloader`; tests pass `makeDownloader:`): every missing file is asked for at once, so reading never waits on the network file by file. While a download has to wait, `phase` is `.starting` (also when onboarding finds a library), so the opening screen shows it. A download whose stream ends without completing goes on to reading.
  - **`opening`** (`LibraryOpening`, Foundation only): the step (`.looking(kind)`, `.downloading(LibraryDownloadProgress)`, `.reading`), `isICloud`, `isStalled`, and the words: `title` ("Downloading 12 of 150 files from iCloud Drive…"), `detail` (bytes), `failureNote`, `fractionCompleted` (the bar), `stalledTitle`, `stalledMessage`, `stalledReasons(onMac:)`. It's stalled after `LibraryStore.openingStallTime` (20 s) without progress (CloudSync's `StallDetector`; a download's progress counts when `hasAdvanced(since:)`).
  - **Stalled:** `keepWaiting()` asks iCloud again for what hasn't arrived and waits another 20 s; `start()` again (Try Again) overtakes the attempt in progress: every attempt has a number, an overtaken one stops its download and drops its results. Neither ever creates a library.
  - **Log:** each step goes to `CloudSync.LibraryLog` (`os.Logger`, subsystem: the bundle id, category `library`): the location, iCloud's answer, the file counts, downloads asked for and failed, the load's files and time, errors. In Console, filter on the category `library`.
- **Sync:** files changed by the other device or a text editor are reloaded automatically, including a change that landed while the library loaded (only those files' entities are replaced, and never a file with an edit waiting to be saved: that save merges the file and reloads it); sync conflicts are merged record by record and listed in `mergedConflicts`. Show them with `LibraryStatusBanners()` or link to `SyncScreen`.
- `LibraryStore.inMemory(library)` holds a library without files (previews, tests).

### PriceStore — prices, FX and inflation

`fetch(for:on:refresh:) async -> CheckInPrices` (never throws; failures are entries with a readable reason; a past date its provider has no price for comes from the provider's history, e.g. gold from `GC=F`, and the entry's `source`, `symbol` and `note` say so), `fetch(for:on:including:refresh:)` (also instruments the library doesn't hold yet, e.g. a position added in a check-in), `testFetch(_ instrument:baseCurrency:on:) async -> PriceListEntry`, `quote(_ instrument:baseCurrency:on:) async -> CheckInPrices` (one instrument's price and its currency's rate, as records that can be saved: the editor's *Test price fetch*), `fetchEach(_ needs:refresh:received:)` (several fetches at once, each result handed over as it arrives; `refresh` clears the session's cache once first: *Update Prices*), `pastPriceNeeds(for:today:) -> PastPriceNeeds` (what *Fill In Past Prices* would fetch; works in previews too), `fillPastPrices(_:in:progress:) async -> PastPriceFill?` (fetches it, a range per instrument at a time, with each step's progress; `nil` in previews), `isFetching`, `canFetch` (false in previews), `lastResult`. API keys come from the Keychain (`KeychainCredentials`, set in Settings).

Prices are saved outside a check-in by the Instruments screen (`Features/Accounts/InstrumentPriceUpdate.swift`): `InstrumentPriceUpdatePlan` (the held instruments with a price source and their currencies, and the months missing of the library's inflation indices, `PriceStore.indices(for:)`), `InstrumentPriceUpdate` (a line per instrument, rate and index; `settle(in:replacingTyped:)` decides what to save against the library as it is, keeping prices and rates typed in by hand for the date, and adding only index months the library hasn't any value for) and `InstrumentPriceUpdater` (fetches with `fetchEach`, saves with one `upsert(prices:fxRates:indices:)`).

*Fill In Past Prices* (`Features/Accounts/PastPriceFilling.swift`, views in `PastPricesViews.swift`): `PastPricePlan` (a `PastPriceLine` per instrument, rate and index with its dates, and later its `PastPriceResult`; `offers(among:library:)` for the import's Done step), `PastPriceFiller` (`prepare`, `run` with `PriceStore.fillPastPrices`, then `LibraryStore.insertMissing(_:)`; `phase`, `statusText`, `reset`), `PastPriceText` (ranges, counts, "CoinGecko · ethereum back to Oct 2025, Yahoo Finance · ETH-EUR (history) before") and `OldPriceNote` (the note under a chart, from Tracker's `Valuator.oldPrices`). `PastPricesSheet` is presented with `.pastPricesSheet(isPresented:)` from the Instruments toolbar, `ImportDoneStep` (for `ImportReceipt.importedInstruments`), and `OldPriceNoteView` under the charts of `AccountDetailScreen` (`AccountDetailData.oldPrices`) and the Overview (`OverviewHistory.oldPrices`).

### Trade history

Accounts that record trades (docs/TRADES.md; UI.md, "Trade history") have their own pieces in `Features/Accounts/`:

- **Logic** (Foundation only): `TradeListData.swift`: `TradeTypeDisplay` (names, icons, the sheet's Buy / Sell / Dividend and *More*), `TradeWording` (a trade's `title`, "Buy 10 VWCE", its `price` in its own currency, "134,75 €", the list's `subtitle`, "at 134,75 € · 12 Aug 2026 · note", and the one-line `summary`, "Buy 10 VWCE at 134,75 €"), `TradeList` (an account's trades by month, newest first, with `TradeListFilter` by instrument and type), `TradeHoldings` (from `Valuator.holdings(of:on:)` and `tradeCash(of:on:)`: each `AccountHoldingRow` with its `averageCost` and `share`, then cash and the total), `TradeIncomeYear` (the ledger's `summary(for:)` by year, in the account's currency) and `TradeIssueNote` (`Valuator.tradeIssues(for:)` and `reconciliation(of:)` in words, each with a `TradeIssueAction`). `AccountDetailData` carries `tradeHoldings`, `incomeYears`, `tradeIssues` and `tradeCount`; its `latest` is the Valuator's snapshot and its new-money ticks the trades' flows. `TradeForm.swift`: `TradeEditorTarget` (what the sheet opens on), `TradeForm` (the fields each type shows, `AmountInput` parsing, `computedAmount` with the date's FX rate, `paidOutside` for a trade paid from or into another account with its default from `Library.defaultSettlement(for:in:)`, `settlementTitle` and `negativeCashHint(_:)`, `Trade.problems` by field, `trade(in:)`, and `preview(in:)`, a `TradeFormPreview` with the `TradeEdit`, the quantity and cash after it, the `newMoney` of a trade paid from outside, and the problems it brings in) and `TradeEditNotes`. A `TradeListItem`'s `amount` is what the trade paid or brought in, and its `settlementLabel` marks one paid from outside the account. `AccountConversionData.swift`: `AccountConversionSummary` (the preview of a switch: openings, buys, sells, estimates counted, months).
- **Views**: `TradeViews.swift` (`TradeHoldingsRows`, `TradeHoldingsGrid` on the Mac, `TradeListRowView`, `TradesTable` on the Mac, `TradeFilterMenu`, `TradeIncomeYearView`, `TradeIssueBanners`, `TradeAmountText`), `TradeEditorSheet.swift` and `AccountConversionSheet.swift`.
- **The check-in**: a trades row (`CheckInRow.isTrades`) starts done, as its trades say (`CheckInRow.followsTrades`, the `.unchanged` state; "From trades", `CheckInWording.stateName(for:)`), and needs nothing typed. It shows `row.derived`'s positions read-only (the review's `positions`), *Add Trade…* (`CheckInWording.addTradePrompt(for:)`; it sets `CheckInSession.tradeRequest` with `addTrade(to:on:)`, and the store rebases the draft when the library changes, so the row follows), its cash read-only when it holds any (`CheckInRow.showsCash`, `CheckInWording.tradeCash`) and its new money from `CheckInTradeFlow` (recorded deposits, trades paid from outside the account as `paidOutside`, plus the cash difference; `CheckInWording.tradeNewMoney` and `tradeFlowDetail`). *Enter From Statement* shows a `.cash` field (`CheckInSession.enterStatementCash`, `editingCash`; `CheckInRowDisplay.showsCashField(_:isEditing:)`, which `CheckInFieldOrder` follows); a typed cash (`CheckInRow.hasStatementCash`) makes the new money editable (`CheckInRowDisplay.canEditTradeFlow`), and `useTradesCash` goes back. *Compare With a Statement* uses `CheckInRow.enterStatementQuantities()` (`stopComparing` drops them); the review lists `CheckInRowReview.mismatches` with `CheckInWarningText.mismatch`, and the changed accounts with those from trades (`CheckInReviewDisplay`).
- **New accounts**: `AccountForm.tracking` (trade history by default for brokerage, crypto and metals: `offersTracking`), and `AccountOpeningForm.openingTrades(for:)`.
- **The Overview**: *Needs attention* has an item per account whose trades have problems, opening it (`OverviewAttention.tradeProblems`: "Directa: 2 problems with trades", counting the same `TradeIssueNote`s as its page).
- Everything that reads what an account holds uses `Valuator.snapshot(of:on:)`, `holdings(of:on:)` or `firstRecordDate(of:)`, never a valuation's `positions` (for a trades account those are only a statement to check).

### Account values

How the app reads an account's values (UI.md, "Account detail"); the logic is in Tracker and `Features/Accounts/`, Foundation only.

- **Own currency.** Tracker's `ValueCurrency` (`.base`, `.account`) picks the currency of `Valuator.value(of:on:in:)`, `series(of:in:grid:from:through:)` and `change(of:from:to:in:)`. In `.account` a dollar account is worth its dollars and needs no exchange rate (only positions priced in a third currency do). `AccountDetailData` shows the value, change, chart and values in the account's currency (`currency`, `amount`, `history`), with `baseValue` (`AccountBaseValue`: `.known` at the day's rate, or `.rateMissing`) under the value; list sparklines use it too. Net worth, subtotals and the sidebar stay in the base currency.
- **Missing values.** Tracker's `MissingValues` says what values lack, from `Valuator.missingValues(of:on:in:)` and `missingValues(in:on:)`: its `gaps`, each a missing price or rate, or an open account without a value (`Gap`: the item, the accounts it leaves incomplete, the dates). Charts draw an incomplete point as a gap in an account's line (`[ChartPoint].completeRuns`, `isolatedPoints`) or a dashed, grey stretch of a total (`segments`), or dashed lines along stacked areas (`StackedAreaData`), never as zero. `MissingValueNote` (`PastPriceFilling.swift`) words the note under a chart, with *Fill In Past Prices…*: `account(chart:netWorth:name:)` from `AccountDetailData.missing` and `missingBaseRates`, `overview(_:accountName:instrumentName:)` from `OverviewHistory.missing`; `OverviewAttention.pastGaps` makes the *Needs attention* items.
- **Empty accounts.** An account that holds nothing (`Valuator.emptySince(of:on:)`: a zero balance, or no cash and no quantity) has nothing to check in, so it's never stale (`AccountStaleness.stale`, `AccountListData.swift`): not in the list, the sidebar, the detail, *Needs attention* or `LibraryStore.staleAccounts`. Once it's been empty for longer than the staleness threshold, `AccountStaleness.emptySince` (`AccountDetailData.emptySince`) makes its page suggest closing it on that day.

### CheckInStore — the check-in in progress

Owns a `Tracker.CheckInDraft`, kept as JSON in `Application Support/<bundle id>/CheckIn/draft.json` until saved, never half-written to the library.

- `begin(on:)` resumes the draft (moved to the date if given) or starts one on the suggested date, then fetches prices into it (unless turned off in Settings). `changeDate(to:)`.
- **Following the library.** The draft is rebased (`CheckInDraft.rebase(onto:)`) when it's resumed, whenever `LibraryStore.revision` changes while it exists (once the library is loaded), and right before saving: rows are refreshed from the current previous and saved valuations, added for new accounts and dropped for deleted or closed ones; what was entered is kept. A value saved on the draft's date elsewhere (the other device) that differs from what was entered becomes the row's `conflict`: it writes nothing until it's settled with `resolveConflict(of:keepingSaved:)` or `resolveConflicts(keepingSaved:)`. `refresh()` rebases by hand.
- Edit: `update { draft in … }`, `updateRow(accountID) { row in row.setBalance(…) }`, `markRestUnchanged()` (accounts without an earlier value are skipped), `setManualPrice(_:for:)`, `setManualFXRate(_:for:)` (typed prices survive re-fetching), `fetchPrices(refresh:)` (the library's instruments and the draft's, so a position added in the check-in is priced; adding one fetches again).
- Read: `draft`, `review` (the new total, waterfall and warnings, from `CheckInDraft.review`), `priceList` (every instrument, rate and index with its source or failure), `isFetchingPrices`, `indices`, `status` (for the accessory: `CheckInStatus` with `summary()`, `isDue`, `hasDraft`, `nextCheckIn`, progress).
- `save() async throws -> CheckInSaveResult` rebases, then writes valuations, prices, FX rates and index values in one `LibraryStore.commit` and waits for the files (moving back the opening date of accounts that open later and got a value, and working out again the automatic flows of values after a past check-in: `CheckInDraft.apply(to:)`). Only then does it delete the draft and start the main plan's run for this month's answer with `PlanStore.recordCheckInAnswer(on:)`, without waiting for it: the confirmation follows `PlanStore.checkInAnswer` (its progress, then the headline), so `result.headline` is `nil`. Only the library's latest check-in does: a past one (`CheckInStore.laterCheckIn(than:in:)`) records no headline and no baseline, and returns `result.laterCheckIn` (`isPast`). A failed write throws and keeps the draft; conflicts found by the rebase just before writing throw `CheckInStoreError.changedElsewhere` and write nothing. `discard()`, `persistNow()` (the root view calls it when the app leaves the foreground), `restoreDraft()` (at launch), `restore(_:indices:)` (puts a check-in back as the draft).

### PlanStore — runs on request, progress, results and whether they're out of date, headlines, baselines

The numbers come from a `PlanEngine` (see `Stores/PlanEngine.swift`): `run(_:)`, `run(_:progress:)` (a `PlanProgressHandler` told where the run is, as a `PlanRunProgress`: `phase` — `.starting`, `.earliestAge`, `.simulating`, `.sustainableSpending`, `.summarising` — `completed` / `total` in the phase's unit, the whole run's `fraction`, the scanned `ages`, the `mode`; the default runs without reporting) and `cachedResults(for:)` (results already computed for exactly that request, without running; `nil` by default). The app uses `PlannerPlanEngine` (`Stores/PlannerPlanEngine.swift`): `Planner.run` with `AppTaxRegistry.standard` (Italy and generic so far), its `PlannerProgress` passed on (a request that needs two runs, a what-if's saving or a focus age, shares the bar between them), results cached per plan, library inputs, kind, focus age and start date. Previews use `PreviewPlanEngine` (made-up years run through the same mapping as a Planner run, no progress) and `PlanPreviewEngine` (`Features/Plan`, with the Planner's details and made-up progress through the phases, over about 20 × its `delay`); `UnavailablePlanEngine` remains for a build without a planner.

**Nothing runs on its own.** Screens call `run` only from a button (Calculate, Recalculate ⌘R, Run What-If, Compare's Calculate) or for something the user asked for that needs results (Save Baseline). The one exception is a check-in recording its month's answer. There's no `scheduleRun` any more: opening a plan, editing it, moving a slider or choosing another age makes results out of date instead.

- `run(_ plan:mode:whatIf:focusAge:) async -> PlanResults?` runs off the main thread and cancels the previous run of the same plan and kind, or joins it when the request is the same, also a check-in's run of the plan (`mode: .fast` for a what-if's quick estimate; `whatIf: PlanWhatIf(retirementAge:retiredSpending:monthlySaving:equityReturn:)` for what-ifs, kept apart in `whatIfResults`; `focusAge:` for the charts at another retirement age, in `focusResults`). `cancel(_:kinds:)` (by default the Plan screens' runs, never a check-in's), `clearWhatIf(_:)`, `cancelWhatIf(_:)`, `clearFocus(_:)`, `isRunning(_:)`, `isRunning(_:_:)` by `PlanRunKey.Kind` (`.base`, `.whatIf`, `.focus`, `.checkIn`), `running`, `errors`.
- **Progress:** `progress` (by `PlanRunKey`) and `progress(of:_:)`, the `PlanRunProgress` of each run in progress, set to `.starting` when it starts, updated at most about ten times a second (an update that would move the bar back is dropped) and cleared when it ends.
- **Out of date:** each kept result has its `PlanRunBasis` (`bases`, `basis(of:_:)`): the plan, `PlanRunInputs` (the library data a run reads), the start date, mode, what-if and focus age. `staleReasons(of:_:plan:whatIf:focusAge:)` compares it with the plan (pass the session's unsaved draft), the library as it is now and the screen's what-if and age, giving `PlanStaleReason`s: `.plan` (not a rename), `.library`, `.whatIf`, `.focusAge`. `adoptCached(_:modes:whatIf:focusAge:)` takes results the engine kept for exactly the current inputs, without running. A run that finishes after an edit keeps its basis, so it shows as out of date.
- `whatIfs` and `focusAges`: each plan's what-if and chosen age, so switching plans and coming back keeps them (not saved).
- `results[planID]`: `PlanResults` — `headline: PlanHeadline` (earliest age and date, confidence, success today and at the target age, sustainable spending, FI progress), `successByAge`, `portfolio` (fan), `markers`, `income`, `taxes`, `spending`, `failure`, what a baseline saves (`start`, `accounts`, `taxParameters`, `years`), `currency` (the plan's, which every amount is in; `nil` from the preview engine), and `details` from the Planner (plan hash, FI number, pensions, net income by year, lifetime taxes, the run's warnings, `headline`, the record written at a check-in, identical to the CLI's, and `reading`, how the plan read the library: its buckets and `schemeSeeds`; `nil` from the preview engine). All plain values that feed the chart components directly.
- `mainHeadline`: the Overview's answer: the main plan's latest results, or its last recorded headline. Never starts a run.
- `recordCheckInAnswer(on:)` starts the main plan's run for a saved check-in (kind `.checkIn`, which the Plan screens join but don't cancel) and returns at once; `checkInAnswer` (`CheckInAnswerRun`: date, plan, `isRunning`, then `headline` or `error`) is what the confirmation follows. `checkInSaved(on:) async` is the run itself: it records the headline (`projections/<plan>/headlines`) and saves the yearly baseline at the year's first check-in. `saveBaseline(for:label:kind:on:)`, `recordedHeadlines(for:)`, `hash(of:)` (a plan's `planHash`, the Planner's).

## Import

`Features/Import/`: one flow for spreadsheets and journals. `ImportFlow` (plain values) holds the file, the mapping, the preview, the user's decisions and the step; `ImportController` (`@Observable`) does the writing: `runImport(in:)` applies the preview with `LibraryStore.commit(backingUpAs: "import")` (`ImportPreview.applyFollowingFlows(to:)`: the import, then Tracker's `Library.followFlows(from:keeping:)` for the automatic flows of the library's values after inserted ones, in the same change and backup), `undoImport(in:)` undoes it with `LibraryStore.undo`, and `saveProfile` writes `imports/<id>.json`.

- **Spreadsheets:** File, Format, Columns, Accounts, Preview, Done, from an `ImportSession` (`ImportFlow+Format`, `+Columns`, `+Accounts`, `+Preview`).
- **Broker transactions** (IMPORT.md, "Broker transactions"): when the session's layout is `trades`, a **Types** step comes between Columns and Accounts (`ImportFlow.steps`). `ImportFlow+Types` holds its logic: `typeRows` (the type column's values, from `ImportSession.tradeTypeValues`), `setTradeType(_:for:)` (a trade type, `.ignore` to leave the rows out), `resetTradeType(for:)`, `amountSign` / `setAmountSign(_:)` and `tradeSignNotes`; the view is `ImportTypesStep`. Columns offers the trade fields (`ColumnUse.options(for: .trades)`) and the account of every row; Accounts shows the proposal to make an account record trades (`AccountChangeProposal.Change.recordTrades`; decisions are kept per account and kind of change, `AccountChangeKey`); `describe(_ trade:)` writes a trade for Preview and conflicts; `ImportReceipt` counts `trades` and names `tradesAccounts`. `ImportPreviewData.trades` is a made-up movements file for previews (`ImportPreviewHost(step:file: .trades)`).
- **Ledger journals** (IMPORT.md, "Ledger journals"): File, Accounts, Commodities, Preview, Done. Accounts that record trades get the journal's trades (`ledgerTradesAccounts`; cash checks with `setLedgerCashChecks(_:)`). `ImportFlow.ledger` holds a `LedgerImportState` (the files, the folders the app may read, the `LedgerJournal`, the `LedgerImportSession`); its preview becomes the flow's, so conflicts, decisions on proposed accounts and instruments, Done, Undo and Save as profile are shared. The logic is in `ImportFlow+Ledger` and `LedgerImportState`, the views in `LedgerFilesStep`, `LedgerAccountsStep` and `LedgerCommoditiesStep`.
- **Reading journals in the sandbox:** `ImportController.openLedger(_:)` reads the chosen files off the main thread through `SandboxLedgerFiles` (`ImportController+Ledger`), which uses the security-scoped access of the file or folder holding each file and `CoordinatedFileAccess`. Includes outside what the user chose are listed (`LedgerJournal.missingIncludes`); **Choose the Journal's Folder…** grants the folder (`grantLedgerFolder(_:)`) and reads the journal again, keeping the mapping.
- **File types:** `Config/Info.plist` declares `org.ledger-cli.journal` (`.ledger`, `.journal`, `.hledger`, `.j`, `.dat`) as a plain-text type the app can open; the file importer allows several files at once.

## Design system

- **Colours** (`Palette`, backed by colour sets in `App/Resources/Assets.xcassets`, light and dark): the asset-class colours in stacking order (`Palette.color(for: assetClass)`: cash blue, bonds orange, equity aqua, gold yellow, crypto magenta, real estate green, other violet, debt red), the categorical `series` slots in fixed order, `accent` (the one hue for everything else), `ink` (actual history and text), `secondaryInk`, `mutedInk`, `gridline`, `axis`, `positive` / `negative` (changes, always with a sign and arrow), status colours (`good`, `warning`, `serious`, `critical`; always with an icon and a label), surfaces (`page`, `card`, `border`). Charts name colours by role with `ChartColor`: `Palette.color(for:)` for washes and fills, `Palette.stroke(for:)` for lines, the edges of stacked areas and small marks (legend swatches, dots, the allocation bars). In light mode the stroke of orange, aqua, yellow and magenta is a darker step of the hue (`seriesStroke`, colour sets `Series…Stroke`), so every line reaches 3:1 on the card and on the page; in dark mode it's the colour itself. Validate any colour change with the dataviz skill's `validate_palette.js`, light and dark.
- **Spacing:** `Metrics` (`xs` 4, `s` 8, `m` 12, `l` 16, `xl` 24, `cardRadius`, `lineWidth`, `barRadius`, `readableWidth`). Icons: `AccountKind.systemImage`, `AccountGroup.systemImage`, `AppSymbol`.
- **Numbers** (`AmountFormat`, locale-aware): `amount(_:currency:precision:)` (`.whole` by default, `.cents` in check-in fields and account detail, `.automatic`), `signedAmount`, `percent`, `number`, `compact` (`312k`, `1,2M` for charts; `compact(_:step:)` with the decimals an axis's ticks need), dates (`shortDate` "30 Sep", `shortDate(_:relativeTo:)` "30 Nov 2021" outside this year, `mediumDate`, `longDate`, `monthName`). Zero never has a sign: an amount that rounds to it reads `0 €`, and `DeltaFormat` gives `DeltaText` no arrow for it. `Decimal.doubleValue` for charts only. **Quantities and unit prices** (`QuantityFormat`, the same everywhere): `quantity` (up to 8 decimals, trailing zeros trimmed), `unitPrice(_:currency:)` (the currency's symbol, 2 decimals from 1 up, 4 significant digits below: `0,004312 €`), `labelled(_:_:)` (a label and its value in one text, so they wrap together), and `AccountPositionText` for a holding's lines. `CalendarDate.dateValue` gives a `Date` (noon, local time).
- **Input:** `AmountInput.decimal(from:locale:)` reads `1.234,56`, `1234.56`, `0,4215` and `−240`; `AmountInput.text(for:)` fills a field. `CurrencyChoices` and `CountryChoices` for pickers.
- **Views:** `AmountText(amount, currency:, precision:, tabular:, animatesChanges:)` — tabular figures, `•••••` while amounts are hidden, `.privacySensitive()`. `DeltaText(amount)` / `DeltaText(percent:)` — ▲/▼, sign and colour, `invertsColor` for debts. `Card("Title") { … }`, `Card { … } header: { SectionHeader("Title") { accessory } }`. `StatusBanner(.info/.success/.warning/.error, title, message:, actionTitle:, action:)`. `LibraryStatusBanners()` shows read-only, save errors, unreadable files and merged conflicts. `.tabularFigures()`.
- **Mac layouts:** a Mac window can't be smaller than the minimum size of its content, so every page's content scrolls (a `ScrollView`, a `List`, a `.grouped` `Form`, or a `Table` that is the whole page), and the window opens at 1200 × 800 with a minimum of 900 × 600 (`CanIRetireYetApp`). Content pinned above or below a scrolling area goes in `OverflowScrollView(maxShare:) { … }`: its own height while that fits, at most that share of the height it's offered, scrolling beyond, never a minimum height (the plan's What-if in the inspector, the import's column settings). Content that never scrolls, above all text with `.fixedSize(horizontal: false, vertical: true)`, which is measured at the narrowest width, makes the window taller than the screen. A table on a scrolling page is a `PageTable` (Mac): column titles and a line per item, as tall as its lines, with click to select, double-click to open and a context menu; each column is a `PageTableColumn` (a minimum and a maximum width) so the lines line up. Not a `Table`, which scrolls on its own and needs a guessed height. The account's values and trades use it.
- **Environment values:** `\.baseCurrency` and `\.hidesAmounts`, set by `appEnvironment`; `AmountText` reads them, so you rarely pass a currency. `\.chartSurface` is what a chart draws the gaps between stacked areas in: the card, or `Palette.page` for the Overview's history chart.

## Library location and sync

At launch `LibraryStore.start()` asks `CloudSync.LibraryLocator` for the iCloud container's `Documents/` (off the main thread) or `Application Support/<bundle id>/Library`, remembers the choice on the device, downloads a library in iCloud Drive that isn't all on the device (`CloudSync.UbiquitousLibraryDownloader`: the folder on disk, then an `NSMetadataQuery`, every missing file asked for at once, `LibraryDownloadProgress` until all are here), and loads through `CloudSync.LibrarySync`: coordinated reads and atomic writes (`CoordinatedFileAccess`), an `NSMetadataQuery` watcher that also downloads files eagerly (polling for a local library), and conflict merging with `Storage.ConflictResolver` (`NSFileVersion`). Nothing on that path touches the files on the main thread. A library on this device can be moved to iCloud Drive from Settings. A library written by a newer app opens read-only.

If the iPhone sticks on the opening screen, Console (on a Mac, with the iPhone connected) shows each step: filter on the subsystem (the bundle id) and the category `library`.

The app only builds on a Mac, but everything that doesn't import SwiftUI (the `Stores/` folder, `AppNavigation`, `SidebarAccounts`, `AmountFormat`, `AmountInput`, the charts' `ChartData`, `ChartLayout`, `ChartScales`, `ChartHorizon`, `ChangeBars`, `IncomeChartData` and `StackedAreaData`, `OverviewData`, `AccountListData`, `AppModel`, `PreviewLibrary`, `PreviewPlanEngine`, the import's `ImportFlow*`, `ImportController*`, `LedgerImportState` and `LedgerPreviewData`, `PastPriceFilling`, the plan's `PlanSession`, `PlanRunState`, `PlanPreviewEngine` and other `Plan*` logic, and the trades logic: `TradeListData`, `TradeForm`, `AccountConversionData`, `AccountDetailData`, `CheckInModel`, `CheckInSession`, and `QuantityFormat`) compiles on Linux too. To type-check and test it there, make a scratch Swift package outside the repository that depends on this one (`Model`, `Tracker`, `Storage`, `Prices`, `CloudSync`), copy those files into a target, and add Swift Testing tests. That's how the stores were tested: loading, editing and saving a copy of the example library, the watcher reloading a hand-edited file, the read-only guard, opening a library (downloading before reading with a fake downloader, the opening screen's words, stalling, Keep Waiting, Try Again overtaking an attempt, a download that can't be followed), a full check-in save, plan runs, `PreviewLibrary` being identical to the example library, the trades screens' logic (the list, holdings, income, issues, the trade form and its previews, the store's trade and conversion helpers, the check-in's trades rows), runs only on request (nothing runs on appear, after edits, slider moves or another age; results out of date for each reason and back up to date when an input is changed back; a what-if's quick then full run; cancelling keeps the old results; editing during a run; a check-in's run that the Plan screen joins but can't cancel; progress from the real and preview engines in order and ending at 1; the progress words in the locale's numbers), and the sidebar's accounts (groups and values matching the list, the remembered expanded state, selecting, closing and deleting the selected account), and the Accounts list's collapsed sections (shared with the sidebar, all expanded while searching), the charts' layout (ticks, labels, scales, the time span, the income chart's and the stacked areas' bands and lines), the preview engine's income going through the Planner's mapping, and *Needs attention*'s items (trade problems, empty accounts never stale). Views can be type-checked too, against a stand-in `SwiftUI` module with the SDK's signatures that draws nothing: copy the view files in with their `#Preview` blocks removed and `#if os(iOS)` / `#if os(macOS)` turned on (Linux is neither), stub the views they use from elsewhere, and add the modifiers the compiler asks for. Chart views work the same way against stand-in `Charts` and `Accessibility` modules with the SDK's signatures, and turning their `#Preview` blocks into functions checks the previews too. That catches wrong labels, types and missing members before CI's macOS job, which stays the real check.
